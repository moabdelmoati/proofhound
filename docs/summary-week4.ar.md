# ProofHound — ملخّص للعرض

## اكتشاف وإصلاح الثغرات بوكلاء ذكيين

مشروع تخرج — ملخّص الفكرة، وما أُنجز حتى الأسبوع الرابع، وما سنصل إليه هذا الترم.

---

## 1. فكرة المشروع

أدوات التحليل الثابت (SAST) تكتشف الثغرات المحتملة بسرعة، لكنها تُطلق إنذارات كاذبة كثيرة فيتجاهلها
المطورون. والـ Fuzzing يؤكّد الثغرة الحقيقية بالتنفيذ، لكنه يحتاج كتابة اختبار (harness) يدويًا بخبرة
ووقت.

**ProofHound** يربط الاثنين تلقائيًا ولكل commit: نتيجة الـ SAST تُوجّه نموذجًا لغويًا كبيرًا لكتابة
الـ harness، ويُشغّله fuzzer في بيئة معزولة، ولا يُبلَّغ عن الثغرة إلا إذا **أكّدها التنفيذ فعلاً** —
ثم يُقترح إصلاح لا يُقبَل إلا إذا أثبتت إعادة التشغيل أن الثغرة اختفت.

**المبدأ الحاكم:** التنفيذ هو الحكم، لا كلام النموذج. وبهذا نقلّل الإنذارات الكاذبة ونعطي المطوّر دليلًا
يعيد إنتاج الثغرة بدل مجرّد تحذير.

**العمود البحثي:** هل فريق من الوكلاء المتخصصين أفضل من وكيل واحد عام؟ نبني الوكيل الواحد هذا الترم،
والنظام متعدد الوكلاء الترم القادم، ونقارن بينهما.

## 2. كيف يعمل (ثلاث خطوات)

1. الـ SAST يجد موضعًا مشكوكًا فيه داخل الكود الذي غيّره الـ commit (المصدر والمصبّ).
2. نموذج LLM يكتب harness موجَّهًا بتلك النتيجة، ويشغّله الـ fuzzer في حاوية Docker معزولة بلا شبكة.
3. إذا حدث عطل وتأكّد بإعادته 3 مرات ← الثغرة مؤكَّدة، ومعها مُدخل يعيد إنتاجها، ثم يُقترح إصلاح.

## 3. ما أُنجز حتى الأسبوع الرابع

البنية التحتية كاملة ومُختبَرة من البداية للنهاية على ثغرات npm حقيقية:

- بيئة Docker معزولة (Jazzer.js)، بلا شبكة وبحدود موارد.
- قراءة الـ diff واستخراج الدوال المتغيّرة لـ JavaScript/TypeScript و Python.
- محلّل بقواعد Semgrep لخمسة أصناف ثغرات (حقن أوامر، اجتياز مسارات، حقن كود، تلويث prototype، ReDoS).
- fuzzer يؤكّد العطل بإعادته 3 مرات، ومنسِّق، وواجهة أوامر، وتقارير JSON و SARIF.
- تكامل GitHub Action يعمل على كل pull request.
- درجة ثقة تدمج إشارة الـ SAST وإشارة الـ Fuzzing.
- مقياس (benchmark) من 31 ثغرة npm حقيقية بحقيقة مرجعية.

**أول نتيجة بحثية:** الـ SAST وحده يكتشف الموضع الصحيح في **30 من 31** حالة، لكنه يُطلق **244 إنذارًا
كاذبًا** (نحو 8 لكل حالة) — وهذا بالضبط ما يبرّر التأكيد بالـ Fuzzing.

> ملاحظة: نحن متقدّمون على خطة الترم؛ المطلوب رسميًا في هذه المرحلة هو مراجعة الأدبيات وتحديد النطاق،
> وقد أنجزنا معه جزءًا كبيرًا من البناء.

## 4. ما سنصل إليه هذا الترم (الترم الأول)

- أداة سطر أوامر تعمل من البداية للنهاية على JS/TS: تحدّد الدالة المتغيّرة ← SAST ← توليد harness ←
  fuzzing ← عطل مؤكَّد بمُدخل يعيد إنتاجه.
- نظام **الوكيل الواحد** يعمل بنموذج حقيقي على المقياس، مع أول الأرقام: معدل الاكتشاف، ونسبة الإنذارات
  الكاذبة قبل التأكيد وبعده، ونجاح الـ harness من أول محاولة وبعد الإصلاح.
- نموذج صغير **تجريبي** مدرَّب على Colab من الـ harnesses الناجحة.
- خط أساس للمقارنة، وتقرير الترم، وعرض توضيحي حيّ أمام اللجنة.

## 5. الترم القادم (باختصار)

نظام **متعدد الوكلاء** والمقارنة بينه وبين الوكيل الواحد، والإصلاح التلقائي للكود، وتدريب النماذج
الكامل في نظام تتابعي، ولوحة عرض للشركات تبقى بياناتها داخلها، ودعم Python في الـ fuzzing، والورقة
البحثية.
