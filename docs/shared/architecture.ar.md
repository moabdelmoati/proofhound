# ProofHound — معمارية المشروع

المعمارية التقنية الكاملة للمشروع عبر الترمين. هذا الملف هو المرجع الأوحد لكيفية تركيب النظام،
بينما يغطّي ملف المقترح (`proposal.ar.md`) الإطار البحثي والخطة.

---

## 1. الهدف والمبدأ

يؤكّد ProofHound ويُصلح الثغرات الأمنية في الكود الذي يغيّره الـ commit. مبدؤه الحاكم هو **التنفيذ هو
الحكم**: لا يُبلَّغ عن شيء كثغرة إلا إذا أعاد تشغيلٌ معزول إنتاجها، ولا يُقبَل إصلاح إلا إذا أثبتت إعادة
التشغيل اختفاء الثغرة. الـ SAST والـ LLM يقترحان، والتنفيذ يقرّر.

تجلس واجهتان فوق نواة مشتركة واحدة:

- **وكيل واحد (الترم الأول)** — نموذج LLM واحد في حلقة استخدام أدوات ينجز العمل كله.
- **متعدد الوكلاء (الترم الثاني)** — وكلاء متخصصون، لكلٍّ دور ثابت، ينسّقهم منسِّق، مع نماذجنا الصغيرة
  في نظام تتابعي تحت نموذج كبير.

ومقارنة «وكيل واحد مقابل متعدد الوكلاء» (RQ3) هي العمود الفقري للبحث.

## 2. التدفّق العام

```
commit ──▶ محلّل الـ diff ──▶ مُكيِّف اللغة ──▶ المحلّل (SAST)
                                                │  نتائج على الدوال المتغيّرة، بترتيب الخطورة
                                                ▼
                                 ┌──────── لكل نتيجة ────────┐
                                 │  الـ Harness ──▶ الـ Fuzzer │
                                 │   (LLM + حلقة إصلاح)        │
                                 │        │ harness صالح       │
                                 │        ▼                    │
                                 │  fuzzing معزول ──▶ عطل؟     │
                                 │        │ إعادة 3 مرات        │
                                 │        ▼                    │
                                 │  الفرز: دمج SAST + fuzzing  │
                                 │   → ثقة، PoV، CVSS          │
                                 │        │ مؤكَّد               │
                                 │        ▼                    │
                                 │  الـ Patcher: إصلاح + اختبار│
                                 │   يُقبَل إذا زال الـ PoV ونجحت│
                                 └──────────────┬──────────────┘
                                                ▼
                     التقارير: JSON · SARIF · تعليق MR · لوحة العرض
```

يقود **المنسِّق** هذا التسلسل، ويملك ميزانية الوقت والـ tokens، ويكتب كل المخرجات في
`runs/<commit>/`. في الترم الأول ينفّذ الوكيل الواحد الصندوق الداخلي كحلقة LLM واحدة، وفي الترم
الثاني يصبح كل صندوق وكيلًا منفصلًا.

## 3. المكوّنات

### 3.1 محلّل الـ diff — `vcs/diff.py`
`git diff -U0 <commit>^ <commit>` ← `{ملف: مجموعة الأسطر المتغيّرة}` لامتدادات اللغة الفعّالة.
الأسطر المضافة/المعدّلة فقط، والحذف يُتجاهَل (فقط الكود الموجود بعد الـ commit يمكن اختباره). وتسمح
بصمة الشجرة الفارغة بمعاملة أول commit في المستودع كأي commit آخر.

### 3.2 مُكيِّف اللغة — `adapters/`
صنف لكل لغة خلف `LanguageAdapter`، ويختاره سجلّ (`get_adapter`) بالاسم. مسؤولياته: استخراج الدوال
المتغيّرة (tree-sitter)، وقالب الـ harness، وبناء أوامر الـ fuzzing/الإعادة/التغطية، وقراءة التغطية،
وتحليل تقارير الـ fuzzer.
- **JavaScript/TypeScript** (`javascript.py`، Jazzer.js): قواعد نحوية واحدة تخدم JS و TS؛ والمرور
  بمؤشّر يتفادى عطبًا في tree-sitter على الملفات الكبيرة (مثبّت `< 0.26`).
- **Python** (`python.py`، Atheris): جانب التحليل مُنفَّذ؛ وخطافات الـ fuzzing في الترم الثاني.
إضافة لغة = مُكيِّف واحد ومجلّد قواعد، دون تغيير الوكلاء.

### 3.3 المحلّل — `agents/analyzer.py`
يشغّل محرّك الـ SAST على الملفات المتغيّرة، ويبقي فقط النتائج داخل دالة متغيّرة، ويرتّبها بالخطورة. تحمل
كل نتيجة (`Finding`): مُعرّف القاعدة، والخطورة، والرسالة، ومعامل المصدر، وتعبير المصبّ، وصنف الثغرة،
والدالة الحاوية.

### 3.4 محرّك الـ SAST — `sast/`
واجهة `SastEngine`؛ و`SemgrepEngine` يشغّل Semgrep في Docker (`--network none`) ويحوّل مخرجاته JSON
إلى نتائج. قواعدنا من نوع taint في `rules/semgrep/<language>/`: المصدر معامل دالة (كود مكتبة) أو
بيانات طلب (كود تطبيق)، والمصبّ هو العملية الخطرة. خمسة أصناف JS اليوم: command injection، path
traversal، code injection، prototype pollution، ReDoS؛ وصنفان لبايثون. تضمّن القواعد علامات
`[source][sink]` لتذكر النتيجة المعامل الملوَّث. والمحرّك قابل للاستبدال — بمحرّكنا أو CodeQL للمقارنة.

### 3.5 وكيل/خطوة الـ Harness — `agents/harness.py`، `orchestrator/manual_harness.py`
بإعطاء الدالة ومسار تصديرها والنتيجة وقالب، يكتب LLM ملف `harness.js`. وتعيد حلقة الإصلاح كل فشل إلى
النموذج عبر سلّم تحقّق — بناء الجملة ← التحميل ← بلوغ الهدف (تغطية) ← نمو التغطية — حتى عدد محاولات
محدَّد، ثم تُوسَم النتيجة `harness_failed`. وتوفّر `ManualHarnessStep` harnesses مكتوبة يدويًا
للتشغيل بلا LLM (الاختبار والعرض الاحتياطي). وتُسجَّل كل محاولة للتدريب (3.11). وكتابة prompt الـ LLM
من إعداد الفريق.

### 3.6 وكيل الـ Fuzzer — `agents/fuzzer.py`
يشغّل الـ fuzzer في البيئة المعزولة للميزانية المحدَّدة مع تفعيل كاشف العطل لصنف النتيجة، ويحفظ corpus
لكل هدف على القرص، ويحلّل المخرجات بحثًا عن تقارير كواشف الأمان. ويُعاد كل عطل مرشَّح **3 مرات**؛ ولا
يصير `Crash` مؤكَّدًا إلا العطل الذي يتكرّر في كل مرة ويبلغ أثرُه الكود الهدف.

### 3.7 الفرز — `agents/triage.py`
يدمج الإشارتين الثابتة والديناميكية في درجة ثقة واحدة في [0، 1]. قائم على قواعد وقابل للتدقيق: عطل
مُعاد ومطابق للصنف ← ≥ 0.90؛ وتشغيل fuzzing نظيف يخفض سابقة الـ SAST (أكثر كلما طال)؛ وعدم المطابقة
في المنتصف؛ وغياب الـ harness يُبقي سابقة الـ SAST وحدها. ويضيف الترم الثاني سكربت PoV مستقلًّا،
وتصنيف عطل بالـ LLM، وتقدير CVSS — تحسّن حقول الشرح فقط، لا الدرجة.

### 3.8 الـ Patcher (الإصلاح التلقائي) — الترم الثاني
لكل نتيجة مؤكَّدة، يقترح تعديلًا أدنى للدالة المصابة واختبار انحدار. يطبّقه على نسخة مؤقتة، ثم **يعيد
تشغيل الـ PoV واختبارات المشروع القائمة**؛ ولا يُقبَل الإصلاح إلا إذا زال الـ PoV ونجحت كل الاختبارات.
ولا يُعدَّل كود التطبيق المصاب في مكانه إلا بعد قبول إصلاح. مكتوب بالـ LLM، ومحكوم بالتنفيذ.

### 3.9 المجدوِل — الترم الثاني
قائم على قواعد: يرتّب الأهداف بالخطورة ويمنح كلًّا شريحة وقت fuzzing داخل ميزانية التشغيلة؛ ويعيد
استخدام الـ corpus المخزَّن لتبدأ الـ commits اللاحقة من تغطية سابقة (fuzzing مستمر).

### 3.10 البيئة المعزولة — `sandbox/docker_runner.py`
يعمل كل مخرج مولَّد في حاوية جديدة: `--network none`، وحدود ذاكرة/معالج/عمليات، وجذر `--read-only`
مع tmpfs للعمل، ومستخدم غير جذر، ومهلة يفرضها المضيف. يُركَّب الهدف للقراءة فقط في `/work/target`،
و`/work/out` قابل للكتابة يحمل الـ harness والـ corpus وملفات العطل. وتُثبَّت التبعيّات مرة واحدة
مسبقًا في حاوية منفصلة متصلة بالشبكة؛ وحاوية الـ fuzzing بلا شبكة أبدًا.

### 3.11 المنسِّق والميزانية — `orchestrator/`
يشغّل التدفّق لكل نتيجة، ويفرض ميزانية وقت + tokens (يتخطّى بقية النتائج عند نفادها)، ويعزل الأعطال
(نتيجة فاشلة لا تُجهض التشغيلة)، ويكتب `runs/<commit>/`. وخطوة الـ harness أي كائن فيه
`produce(finding, target, out) -> Harness`، فيدخل الوكيل الواحد أو وكيل التعدّد أو الخطوة اليدوية
بنفس الطريقة.

### 3.12 مسجّل بيانات التدريب — `datalog/logger.py`
يضيف سطر JSON لكل محاولة harness (الـ prompt، والمخرج، ونتائج الفحص بكل مرحلة، والـ tokens، والنموذج).
وتُوسَم محاولات حالات التقييم وتُستبعَد من التدريب (منعًا للتسرّب). والمحاولات المُتحقَّق منها هي مجموعة
التقطير للنماذج.

### 3.13 التقارير — `reporting/`
- **JSON** (`report.json`): التشغيلة كاملة — النتائج والحالات والأعطال والثقة والأزمنة والـ tokens.
- **SARIF** (`report.sarif`): SARIF 2.1.0 لـ code scanning في GitHub/GitLab؛ وتحمل النتائج المؤكَّدة
  `security-severity` لتظهر داخل الـ PR.
- **تعليق MR** (الترم الثاني) و**لوحة العرض** (القسم 5) يقرآن نفس الـ JSON.

## 4. وكيل واحد مقابل متعدد الوكلاء

| | وكيل واحد (الترم الأول) | متعدد الوكلاء (الترم الثاني) |
|---|---|---|
| التحكّم | حلقة LLM واحدة | منسِّق + وكلاء متخصصون |
| الأدوات | قراءة ملف، SAST، كتابة harness، fuzzer، اقتراح إصلاح | كل وكيل يملك أدواته |
| النماذج | نموذج واحد | نماذج صغيرة لكل وكيل في نظام تتابعي تحت نموذج كبير |
| المشترك | البيئة المعزولة، SAST، الـ fuzzer، المقياس، التقارير، اللوحة | نفسه |

تقارنهما RQ3 على نفس الحالات والميزانيات، قياسًا للاكتشاف والإنذارات الكاذبة وصحة الإصلاح والكلفة.

## 5. لوحة العرض الذاتية الاستضافة — الترم الثاني

لوحة ويب تُنشَر داخل المؤسسة. تقرأ JSON من `runs/` (وقاعدة بيانات محلية صغيرة) وتعرض لكل مشروع مفحوص
(تطبيقات ويب وخدمات):

- الثغرات المؤكَّدة مع الخطورة والـ PoV والمُدخل الذي يعيد الإنتاج؛
- أي النتائج لها إصلاح مقبول وأيّها ما زال مفتوحًا؛
- التاريخ عبر الـ commits.

**الخصوصية بالتصميم.** تعمل اللوحة وخط المعالجة والبيئة المعزولة وقاعدة البيانات كلها على أجهزة المؤسسة
نفسها. ولا يغادر الكود المصدري ولا النتائج ولا أدلة الـ PoV شبكتها. والنداء الخارجي الوحيد هو واجهة
النموذج الكبير الاختيارية، ويمكن استبدالها بنموذج ذاتي الاستضافة ليصبح النشر دون اتصال تمامًا. ولا
توجد قياسات تتبّع (telemetry).

## 6. نموذج الأمان

- المحتوى المُلاحَظ (الكود، رسائل الـ SAST، وثائق التبعيّات) **بيانات لا تعليمات** — لا يغيّر سلوك
  الوكلاء.
- كل كود مولَّد غير موثوق ولا يعمل إلا في البيئة المعزولة (3.10).
- الأسرار (مفتاح النموذج الكبير) تُقرأ من البيئة، ولا تُسجَّل، ولا تُرسَل للبيئة المعزولة.
- تُفَكّ الحزم المُنزَّلة في مجلّدات معزولة لكل حالة.

## 7. التقنيات

| الحاجة | الاختيار | السبب |
|---|---|---|
| المنسِّق / الوكلاء | Python 3.11+ | Semgrep و Atheris والتدريب كلها Python |
| التحليل النحوي | tree-sitter (JS/TS، Python) | أسلوب واحد لكل لغة |
| الـ SAST | Semgrep في Docker (وضع taint) | قابل للاستبدال، بلا تثبيت أصلي |
| الـ Fuzzer (JS/TS) | Jazzer.js | موجَّه بالتغطية، كواشف أمان |
| الـ Fuzzer (Python) | Atheris | نفس النموذج للغة ثانية |
| البيئة المعزولة | Docker | بلا شبكة، حدود موارد |
| الوصول للـ LLM | عميل محايد المزوّد (Anthropic / OpenAI / متوافق / محلي) | تبديل النماذج لكل وكيل، وقابلية الاستضافة الذاتية |
| واجهة الأوامر | Typer | analyze، scan، benchmark-sast |
| النماذج | نموذج كود مفتوح + مُكيِّفات LoRA بـ QLoRA | تخصيص رخيص لكل وكيل على Colab |

## 8. بنية المستودع

```
src/proofhound/
  models.py          الكائنات المعرَّفة المتبادلة بين المكوّنات
  config.py, cli.py  الإعدادات وسطر الأوامر
  vcs/               تحليل الـ diff
  adapters/          لكل لغة: javascript، python، السجلّ
  sast/              واجهة المحرّك + Semgrep
  agents/            analyzer، scheduler، harness، fuzzer، triage، patcher
  orchestrator/      pipeline، budget، خطوة harness اليدوية
  llm/               عميل محايد المزوّد، النظام التتابعي
  sandbox/           مشغّل Docker
  reporting/         json، sarif (اللوحة في الترم الثاني)
  datalog/           مسجّل بيانات التدريب
  benchmark/         باني حالات SecBench.js، مُقيّم الـ SAST
docker/jazzerjs/     صورة البيئة المعزولة
rules/semgrep/       قواعد taint لكل لغة
benchmark/cases/     الحالات المبنيّة (case.yaml مُودَع، repo/ يُعاد بناؤه محليًا)
training/            دفاتر QLoRA وبيانات التدريب
experiments/         النتائج (RQ1–RQ6)
docs/                المقترح وهذه المعمارية
```

## 9. عقد البيانات

يقرأ كل مكوّن ويكتب الكائنات المعرَّفة في `models.py` فقط — `ChangedFunction`، `Finding`،
`Harness`، `Crash`، `TriageResult`، `Patch`، `FindingResult`، `RunReport` — فيُبنى كلٌّ ويُختبَر
منفردًا وتتبادل الواجهتان الواحدة والمتعددة مواضعهما. ويُسجَّل `produced_by` (صغير/كبير/لا شيء) على
الكائنات المولَّدة ليُقاس RQ6 من اليوم الأول.
